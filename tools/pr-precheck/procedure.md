# Procedure: how this tool grades a PR package

These steps grade a pull request; they do not make one. Follow them in order and use only the package (in eval mode, the bundle text; in live mode, the locations named in references/evidence-guide.md). If a step says to note something, keep the note short and quote the exact words from the package. If a step is silent about something you need, say so in the summary instead of inventing a step.

In live mode, SKILL.md has already had you read scope.md (and stop if its Repo line is a placeholder or the work is outside the scoped repo) and voice-guide.md before step 1 below. In eval mode, skip both.

## Read order

Read the parts in this order. The order matters for the side-by-side checks later: the plan is read first so the diff is judged against what was promised, not against how the description talks about it, and the description is read last so its claims are judged against what the diff and the test evidence actually show.

1. Read the **plan** (live: plan.md including Deviations; eval: the plan context). Note the stated cause, the stated change, what is named as in and out of scope, every file or folder it names, every case its test plan names (the issue's input, controls, edge or nested cases), and anything under Deviations or an equivalent note.
2. Read the **repo's stated standards** (live: .github/PULL_REQUEST_TEMPLATE.md, docs/CONTRIBUTING.md and the issue thread; eval: the repo-facts part). Note the PR template's sections, its issue-link line and its checkbox list, the checks the repo tells contributors to run, the AI-use disclosure rule if there is one, and any other explicit ask (changelog, docs, marker or suppression cleanup, branch and commit conventions). If the issue thread shows a claim or maintainer request, note it.
3. Read the **diff** (live: the output of `git diff main...HEAD`, with `--stat` for the file list; eval: the diff part). First list every changed file. Then read the hunks and note: which hunks are source changes, which are tests, any test or marker removals, and any hunk that looks like debris (debug prints, commented-out code, whitespace-only or reformatting churn, files unrelated to the plan).
4. Read the **test evidence** (live: test_evidence.md; eval: the test-evidence part). Note each command and the output printed under it. Mark any result that has only a sentence, a note after `#`, or a placeholder such as `[paste output here]` in place of printed output.
5. Read the **description** last (live: pr_draft.md, title on the first line; eval: the title and description part). Note the title, whether each template section has real content, the issue number after `Closes #`, which boxes are ticked, every factual claim about the change or its testing, and what the Notes for Reviewers say (AI-use disclosure, deviations, anything left out on purpose).

## Evidence gathering

For each check, pull exactly this and record it before grading. Do not hunt anywhere else.

1. **plan-fidelity**: put the diff's file list beside the plan's named files and folders. A plan that names a file's folder, or "a changelog entry", names that file. For each changed file record one of: named by the plan, explained in Deviations, or neither. For each change the plan promised, record whether it appears in the diff, and if it does not, whether the description or Deviations discloses why. For a file that is neither named nor explained, record whether the fix visibly needs it.
2. **description-matches-diff**: list every factual claim in the description (Summary, Changes bullets, and statements such as "exactly as planned", "no changes beyond the plan", "no options added", "tests added"). For each, find the diff line that proves it and record yes or no. A claim that something was not added is yes if nothing in the diff adds it. Then scan the diff for a meaningful change the description never mentions and record it.
3. **tests-cover-plan**: list each case the plan's test plan names (the issue's input, each control, each edge or nested case). For each, record how it is covered: a test in the diff, a result reported in the test evidence (for example a control re-run with its result stated), or neither. Also list each test the description's checklist or Changes claims was added and confirm a matching test exists in the diff. Record any omission the description or Deviations discloses, with its stated reason.
4. **test-evidence-observable**: find the decisive proof the plan's test plan names (the repro re-run before and after, or the failing-then-passing test). For each of the before and the after, record the command or action and the specific result observed (printed output, or concrete values such as exact error text, exit code, rows, toast text, URL; a concrete result written as a comment beside the command counts). Mark any that rests only on a verdict word ("passes", "works", "matches", "unchanged") or a placeholder. Place the before result beside the after result and record whether they differ in the way the plan's test plan predicts. Leave secondary results (a suite or lint summary, a control) for the other checks.
5. **repo-checks-reported**: list only the checks the repo's PR template or contributing doc names. For each, record whether the PR states its result (command output, a summary line, or a stated "passes" or "clean" for that named check), whether its box is ticked, whether any shown output contains a failure, and whether the description acknowledges a failure or a skipped check with a reason. A check the repo does not name is not recorded. If the repo names no check commands, record only whether any shown output reveals an unacknowledged failure. Record a box that can only be satisfied after the PR is opened (such as CI) as not required.
6. **diff-free-of-debris**: walk the hunks from Read order step 3. For each, record whether it serves the planned change or a recorded deviation. Record every hunk that is a debug print, commented-out code, a whitespace-only or reformatting change, a bulk lint or format fix, or a change in a file that does not belong to the change.
7. **template-complete**: list the template's sections (if the repo has no template, note that). For each, record whether it has real content, an explicit "N/A" with a reason, or only the template's placeholder comment. Record the issue number the description references (on the template's issue line if it has one) and compare it to the issue the plan is for. For each ticked box or stated requirement, record whether the diff or the evidence contradicts it.
8. **repo-asks-honored**: list each explicit ask from Read order step 2 that applies to this change (AI-use disclosure, changelog or docs, required marker or suppression cleanup, conventions the package shows). For each, record where the diff or the description meets it, or the reason the description gives for it not applying. Skip an ask the package gives no way to check.
9. **summary-states-why**: take the Summary and Notes for Reviewers and put them beside the plan's cause and change. Record whether they say what the problem was and why this change fixes it.

## Check execution

1. Run the checks in the rubric's table order, from plan-fidelity to summary-states-why. Grade each one `pass`, `fail` or `unclear`.
2. Grade each check only from the notes recorded in Evidence gathering. Do not re-read the whole package for a check; go back to the one part named for it only if a note is missing or you cannot quote it.
3. Apply the pass condition in the rubric to the notes. If the pass condition is met, grade `pass`. If the failure description in the pass condition matches the notes, grade `fail`. Make the call; do not use `unclear` because the judgment is hard.
4. Before failing plan-fidelity, tests-cover-plan or repo-checks-reported, look in the description, the Notes for Reviewers and the Deviations for a disclosure of the shortfall with a reason. If one exists, the shortfall does not fail that check. A disclosure never rescues a claim the diff contradicts (description-matches-diff), a result with no printed output (test-evidence-observable), debris or unrelated hunks (diff-free-of-debris), or an ignored repo ask (repo-asks-honored).
5. A part is "missing" only when the package does not contain it at all, so the check cannot be judged (for example, no plan to compare the diff against, or no repo-facts part to learn the template from). A part that is present and says "none", "N/A", an empty diff, or "no tests added" is present evidence of absence: grade the check normally against it, usually as a `fail`. Grade `unclear` only when a part is missing in the first sense.
6. Write one line of evidence per check, quoting the words from the package that decided the grade (under 15 words per quote). For a `fail` or `unclear`, say which part of the pass condition was not met. Judge the artifacts, not the polish: a long, confident description is not evidence.
7. Do not let one check's grade change another's. Grade each check on its own evidence. The one exception is step 4 above: a disclosure you find is taken into account by each check it applies to.

## Verdict assembly

1. List the grades of the required checks. Preferred checks are graded and reported but are not used for the verdict.
2. If every required check is `pass`, the verdict is `accept` (ready to submit).
3. If any required check is `fail`, the verdict is `reject` (hold).
4. An `unclear` on a required check counts as `fail`, so the verdict is `reject` (hold).
5. In the summary, quote the words from the package that decided the grade for the deciding check. For `reject`, the deciding check is the first required check, in table order, that is not `pass`. For `accept`, quote the evidence for the plan-fidelity check.
6. In live mode, add any voice-guide rules the title or description breaks to the summary, quoting the rule. They do not enter the verdict.
7. End with the fenced JSON block in the output format SKILL.md requires: one entry per check (name exactly as in the rubric, grade, one-line evidence) and a verdict of `accept` or `reject` matching steps 2 to 4. The JSON block must be last.
