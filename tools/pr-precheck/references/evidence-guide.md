# Evidence guide: where evidence lives in a PR package

In an eval package (for example `calib-01.md`), the parts appear as these headings: `## Repo facts` (repo description, whether there is a PR template, the contribution policy and any AI policy), `## Issue`, `## Thread highlights`, `## Plan context` (the repro evidence the plan built on, then the plan with its `Files:` line, what is not in scope, and the test plan), and `## Candidate PR` with the sub-headings `### Title`, `### Description`, `### Commits`, `### Diff` and `### Test evidence`. The bundle is the whole world: nothing outside it is evidence.

In live mode, the same parts are: `plan.md` (including its `## Deviations` section) in the top folder of the clone; the diff from `git diff main...HEAD` (and the file list from `git diff main...HEAD --stat`); the commit list from `git log main..HEAD --oneline`; `pr_draft.md` (title on its first line, then the filled-in PR template); `test_evidence.md`; the repo's `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`; and the issue's thread on GitHub. Only committed changes are in the diff. `plan.md`, `pr_draft.md` and `test_evidence.md` are read from the working directory and are never committed.

## Plan fidelity (harness category: silent-drift)

**Where it lives.** The plan's boundary is in the plan context (eval) or `plan.md` (live): the `Files:` line, the in-scope and not-in-scope statements, and the change it describes. Live, an honest mid-build change is recorded under `## Deviations` at the end of `plan.md`. What actually changed is in the Diff (eval) or the output of `git diff main...HEAD` (live): read the file list first, then the hunks. The description's fidelity claims ("implements the plan exactly", "no changes beyond it", "no options added", the Changes bullets) are in the Description (eval) or in `pr_draft.md` (live).

**What good looks like.** Every changed file in the diff is named by the plan (a plan that names a file's folder, or "a changelog entry", names that file) or is explained in the Deviations notes, and every change the plan promised is in the diff or its absence is disclosed with a reason. Every claim in the description is true of the diff. Silent drift runs both ways: the diff does more than the plan (an extra file, an extra behavior change, a fidelity claim a hunk contradicts) or less than the plan (a promised change that never arrives and is never mentioned). An honest deviation re-ties a mismatch only when it is written down in the plan's deviation notes or the description, not when it exists only in the diff.

## Test evidence (harness category: not-tested)

**Where it lives.** The proof is in `### Test evidence` (eval) or `test_evidence.md` (live), and the Testing section of the description repeats or summarizes it. Read it against the plan's test plan (which cases it names, and what result it says to expect after the fix) and against the repro steps in the plan context (live: your unit 2 repro steps). Which cases the PR tests is in the Diff (eval) or the diff's test files (live): look for a test fixture or test function for every case the plan's test plan names. The checks the repo tells contributors to run are named in the repo's PR template and contributing doc (eval: the repo-facts part; live: `make test-unit`, `make test-integration`, `make lint` and `make typecheck` from the PR template).

**What good looks like.** The decisive proof shows, for the before (on `main`) and the after (on the branch), the command or action and the specific result observed: printed output, or for a tool whose result is not a printed table (a terminal UI, an editor, a browser), the concrete values seen, such as the exact error text, exit code, rows, toast text or URL. A concrete observed result written as a comment beside the command counts. The after differs from the before in the way the plan's test plan predicted. The checks the repo names (in Path Review: `make test-unit`, `make test-integration`, `make lint`, `make typecheck`) are each accounted for: output, a summary line (for example "1462 passed, 12 skipped"), a stated "passes" or "clean" for that check, or a reason it was skipped or is failing. A check that fails is shown with the reason stated; that still counts as evidence. A command that prints "no tests ran" because the repo has none (as `make test-integration` does in Path Review) counts as evidence when pasted as is. Controls the plan names are covered by a test in the diff or by a stated re-run result in the test evidence. Not decisive: a verdict word with no observed specifics ("passes", "works", "fixed", "matches", "unchanged") standing as the proof of the fix, a `[paste output here]` placeholder, or a before and after that cannot be told apart. A check the repo does not name is not required. A case the plan names with no test, no reported result and no disclosure, or a test the description claims that the diff does not contain, is a gap.

## Diff quality (harness category: unreviewable)

**Where it lives.** The change itself is in the unified diff (eval: `### Diff`; live: `git diff main...HEAD`, with `--stat` for the file list) and the commit list (eval: `### Commits`; live: `git log main..HEAD --oneline`).

**What good looks like.** A reviewer can find the change at once: every hunk serves the planned change or a recorded deviation, and the file list in `--stat` contains only files the fix needs (the source change, its tests, and anything the repo requires with it, such as a removed test marker). Debris tells: a debug print or log line left behind, commented-out code, a dead helper or unused import, whitespace-only or reformatting churn, a bulk lint or format fix, a drive-by edit in a file the plan never mentions, or a generated or local file riding along. Debris costs the PR even if the description mentions it, because the reviewer still has to sort through it.

## Standards and comms (harness category: standards-wall)

**Where it lives.** The repo states its asks in the repo-facts part (eval: whether there is a PR template, the contribution policy, any AI policy, anything about how PRs must be sized or linked) or, live, in `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` (sections for branch names, commit messages, the pull request process, seeded-bug `xfail` markers and their `pyproject.toml` suppressions, and not bulk-fixing lint). The issue thread (eval: Thread highlights) shows any claim or maintainer direction. The PR honors them in the description's sections (eval: `### Description`; live: `pr_draft.md`: Summary, Issue, Changes, Testing, Screenshots / Demo, Notes for Reviewers), in the diff (for example a removed marker, a changelog file), and in the branch name and commit messages when the package shows them.

**What good looks like.** Every template section has real content or an explicit "N/A" with a reason, the issue line names the same issue the plan is for (`Closes #` followed by the plan's issue number), and no ticked box or stated requirement is contradicted by the diff or the evidence. A box that can only be satisfied after the PR is opened, like CI, may be left unticked. Any disclosure the repo or course asks for is present: how AI was used goes in Notes for Reviewers, with anything changed from the plan or left out on purpose. Other asks that apply are met (the seeded-bug `xfail` marker removed, the branch named `<type>/<issue-number>-<short-description>`, a changelog entry where the repo wants one), or the description says why one does not apply. Boilerplate looks like the template's placeholder comments left in place, an empty section, a wrong or missing issue number, a box or requirement the package contradicts, or a required disclosure missing. An ask the package gives no way to check is not held against the PR. Whether the description's claims match the diff is plan fidelity, above, not a comms problem.
