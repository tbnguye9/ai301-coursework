# Rubric: is this pull request ready to submit?

A pull request is ready when a maintainer could read it, find that the diff does what the plan said (no more, no less) and what the description says, see proof the change works that they can verify for themselves, review the change without digging through debris, and find that the repo's stated asks were followed. Each check below judges the outcome itself, never the shape or polish of the write-up. A PR that honestly discloses a shortfall (something left out, a check that fails, a change the plan did not name) can still be ready; a PR that quietly does more, less, or something different than it claims is not.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The files and behavior the diff changes, read against the plan's stated scope and change, plus the plan's Deviations notes. | Pass if every changed file and behavior in the diff is inside the plan or explained in the Deviations notes, and every change the plan promised is in the diff or its absence is disclosed (in Deviations or in the description) with a reason. Fail if the diff touches a file or behavior the plan and Deviations never name and that the fix does not visibly need, or if a promised change is missing from the diff with no disclosure. A file the fix genuinely needed that the plan missed passes only if Deviations says so. | required |
| description-matches-diff | Every factual claim in the PR description (Summary, Changes bullets, statements like "exactly as planned", "no changes beyond the plan", "no options added") read against the diff. | Pass if each claim is true of the diff: nothing the description says was changed is missing from the diff, and no fidelity claim ("exactly", "nothing else") is contradicted by a hunk. Fail if any claim is contradicted or unsupported by the diff, or if the diff contains a meaningful change the description never mentions. A claim that something was not added is true if nothing in the diff adds it. | required |
| tests-cover-plan | The cases named in the plan's test plan (the issue's input, controls, edge or nested cases), read against the tests added or changed in the diff, the results reported in the test evidence, and what the description's checklist says was tested. | Pass if every case the plan's test plan names is covered: by a test in the diff, or by a result reported in the test evidence for that case (for example a control that was re-run and its result stated), or its omission is disclosed in the description or Deviations with a reason. A manual re-run is enough for a case the plan itself plans to check by re-running. Fail if the description or checklist says a test was added for a case and the diff contains no such test, or if a case the plan names has no test, no reported result and no disclosure. | required |
| test-evidence-observable | The decisive proof in the test evidence: the before and after re-run of the repro steps (or the failing-then-passing test) that the plan's test plan names, read against that test plan's expected result. | Pass if the before and the after each show the command or action together with the specific result that was observed (printed output, or for a tool whose result is not a printed table, the concrete values seen: exact error text, exit code, rows, toast text, URL), and the after differs from the before in the way the plan's test plan predicts. A concrete observed result written as a comment beside the command counts. Fail if the decisive proof rests only on a verdict word with no observed specifics ("passes", "works", "fixed", "matches", "unchanged"), on a placeholder such as `[paste output here]`, if before and after cannot be told apart, or if there is no before or no after. Honest output that shows a failure still counts as evidence. Secondary results (a suite or lint summary, a control) are graded under repo-checks-reported and tests-cover-plan, not here. | required |
| repo-checks-reported | The checks the repo's PR template and contributing doc name as required or expected (for example test, lint, typecheck, format), read against the test evidence and the ticked boxes in the description. | Pass if every check the repo names is accounted for: the PR states its result (command output, a summary line, or a stated "passes" or "clean" for that named check), or says it was skipped or failing and gives the reason, and nothing shown contradicts a stated result. If the repo names no check commands, pass unless shown output reveals a failure the description does not mention. Fail if a check the repo names is never mentioned at all (not reported, not skipped), if shown output contains a failure the description does not acknowledge, or if a ticked box is contradicted by the evidence. A check the repo does not name is not required. A box for something that can only exist after the PR is opened (such as CI results) may be left unticked and is not a fail. | required |
| diff-free-of-debris | Every hunk in the diff, read against the plan's change. | Pass if every hunk serves the planned change or its recorded deviation, so a reviewer can find the change without sorting through noise. Fail if the diff contains debug prints, commented-out code, unrelated edits (reformatting, whitespace-only churn, drive-by cleanups, bulk lint or format fixes), or files that do not belong to the change, even when the description mentions them. | required |
| template-complete | The PR description read against the repo's PR template (its sections, its issue-link line if it has one, its checkbox or requirements list). | Pass if every template section has real content or an explicit "N/A" with a reason (not the template's placeholder comment), the description references the same issue the plan is for (on the template's issue line if it has one, anywhere in the description if it does not), and no ticked box or stated requirement is contradicted by the diff or the evidence. If the repo has no PR template, pass when the description references the plan's issue. Fail if a section is empty or left as placeholder text, the issue number is missing or different from the plan's, or a ticked box or stated requirement is contradicted by the package (for example "changelog added" with no changelog in the diff). | required |
| repo-asks-honored | The repo's stated policy and contributing asks (AI-use disclosure, changelog or docs requirements, required test-marker or suppression cleanup, branch and commit conventions where the package shows them), read against the description, diff and test evidence. | Pass if every ask that applies to this change is met, or the description says it does not apply and the reason holds. This includes the disclosure of how AI was used if the repo or course asks for one. Fail if an applicable ask is ignored (no AI disclosure when one is required, a required marker or file left behind, a convention visibly broken). An ask the package gives no way to check is not held against the PR. | required |
| summary-states-why | The Summary and Notes for Reviewers, read against the plan's cause and change. | Pass if the Summary says what the problem was and why this change fixes it, in terms that match the plan, so a reviewer understands the intent before reading the diff. Fail if it only restates the title or says what files changed with no reason. | preferred |

## Verdict rule

Accept (ready to submit) if every required check passes. Reject (hold) if any required check fails. An `unclear` grade on a required check counts as a fail, so use `unclear` only when the evidence the check needs is truly missing from the package, never because the judgment is hard. Preferred checks are reported but never change the verdict.

Honest disclosure is part of the evidence, not a loophole. A shortfall the PR itself states, with a reason (a left-out test, a failing check, a change the plan missed), does not fail the checks that grade fidelity, coverage, or test results. It does not excuse a claim the diff contradicts, a result with no printed output, unrelated hunks or debris in the diff, or an ignored repo ask. Grade the thing the PR actually contains, not how polished its explanation is.
