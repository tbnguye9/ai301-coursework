# Rubric: is this plan ready to post and build from?

A plan is ready when a stranger could read it, trust that its diagnosis fits the reproduced evidence, and start building one bounded change that they could then verify. Each check below judges the outcome, not the shape of the write-up.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-fits-evidence | The plan's stated cause, read against the steps, inputs and observed results in the Repro evidence section. | Pass if the stated cause would produce exactly the failure the Repro evidence shows (same input, same symptom) and nothing in the Repro evidence contradicts it. Fail if the cause is asserted without any link to what the repro observed, or if the repro shows something the cause cannot explain (a different input, a different symptom, a different component). Unclear only if the Repro evidence is missing. | required |
| change-addresses-cause | The plan's stated cause read against the plan's stated change. | Pass if the change removes the stated cause, so the bug cannot recur through the same path. Fail if the change only hides or works around the symptom (special-casing the reported input, suppressing the output, adding a retry) while the stated cause stays in place. | required |
| scope-bounded | The plan's scope statement (what changes, what does not) read against the files and behavior the plan says it will touch. | Pass if the plan describes one bounded change, names where it lands, and says what it will not touch, and the stated change alone is enough to fix the reported bug. Fail if the change grows beyond the reported bug (refactors, extra features, "while I'm here" cleanups), or if the boundary is so vague that the size of the change cannot be judged. | required |
| stranger-can-start | The plan's list of files, functions or locations to change, and its approach. | Pass if a contributor who has not seen the repro could open the named location and begin the change without asking what the plan means. Fail if the location or the action is left open ("fix the handler somewhere", "update the logic as needed"). | required |
| test-shows-fix | The plan's test plan read against the repro steps in the Repro evidence. | Pass if the test would visibly differ before and after the fix, by re-running the repro steps (or an automated check built from them) and stating what must be observed afterwards. A manual re-run of the repro is enough; the test does not have to be automated. Fail if the test could pass with the bug still present, does not exercise the changed code path, or states no observable expected result. | required |
| claims-match-certainty | The plan's diagnosis, risks and unknowns, and the plan comment, read against what the Repro evidence actually establishes. | Pass if everything stated as fact is established by the Repro evidence, and anything the repro did not establish is stated as unknown or as a risk. Fail if the plan or comment presents a guess, an untested assumption or an unreproduced behavior as confirmed. A plan with no risks section passes if it overclaims nothing. | required |
| comment-fits-thread-and-repo | The plan comment read against the Thread highlights (existing comments, claims, maintainer requests) and the Repo facts (contribution policy, bug-report conventions, AI disclosure rules). | Pass if the comment does not contradict or ignore the thread or the repo's stated conventions: it does not duplicate or step on someone else's claim, it respects what a maintainer asked for, and it includes any disclosure or format the contribution policy requires. A comment that acknowledges a relevant policy note passes. Fail if it ignores a stated requirement, or says "same as above" instead of giving its own plan. | required |
| comment-matches-plan | The plan comment read against plan.md. | Pass if the comment summarizes the same cause, change and test as the plan and promises nothing the plan does not contain. Fail if the comment adds scope, promises a date or outcome the plan does not support, or contradicts the plan. | preferred |

## Verdict rule

Accept (ready) if every required check passes. Reject (hold) if any required check fails. A `unclear` on a required check counts as a fail, so use `unclear` only when the evidence the check needs is truly missing from the package, never because the judgment is hard. Preferred checks are reported but never change the verdict.
